2. Cryptography Explained

Interactive simulations demonstrating collision-resistant hashing and digital signatures.

SHA-256 (Secure Hash Algorithm 256-Bit)

A cryptographic hash function mapping arbitrary input data into a fixed 256-bit (64 hex characters) digest. It provides pre-image resistance (one-way), second pre-image resistance, and collision resistance.

The Avalanche Effect ensures that changing even 1 bit changes roughly 50% of the resulting digest bits. The client detects this digest mismatch at Step 7 and deletes the downloaded archive without extracting a single byte.

Ed25519 Asymmetric Digital Signatures (RFC 8032)

Ed25519 uses the twisted Edwards curve Curve25519 with SHA-512. It provides 128-bit security level with collision resistance, resistance to side-channel attacks, and ultra-compact 64-byte signatures.

Integrity Verification vs. Publisher Authenticity

Why neither a hash alone nor a signature alone is sufficient for secure software distribution.

Security Dimension SHA-256 Hashing Only Ed25519 Signature Only Combined Two-Tier Architecture (Our System)
What It Verifies File integrity against accidental bit-rot or tampering against a reference hash. Publisher authorship and non-repudiation of the metadata manifest. Both origin authenticity of the publisher AND exact binary integrity of the package.
Adversary Vector Vulnerable: Attacker modifies file AND recalculates reference hash in unsigned manifest. Inefficient: Signing a multi-gigabyte binary directly requires streaming crypto or complex chunking. Secure: Ed25519 signs the canonical manifest containing the SHA-256 hash. Modifying package breaks hash; modifying manifest breaks signature.
Key Management No cryptographic keys required. Asymmetric keypair (Public / Private). Publisher keeps private key offline; client pins public key; server hosts signed bundle.
Server Compromise Breached: Rogue server can push any malicious package. Protected: Rogue server cannot forge valid signatures. Fail-Secure: Even if the update server is fully compromised, clients reject forged updates at Step 2 or 7.

4. Attack Simulations

Interactive test lab executing actual attack scenarios against the client verification engine.

6 Real Scenarios

Scenario 1: Genuine Release

Baseline

Genuine v1.1.0 update signed with official Ed25519 publisher key. SHA-256 hash strictly matches.

Target Outcome: All 11 steps pass; app cleanly upgraded to v1.1.0.

Scenario 2: Package Tampering

Integrity Attack

Adversary intercepts network package and injects malicious bytes into the ZIP archive.

Blocked At: Step 7 (Verify Package Hash Match). Package purged before extraction.

Scenario 3: Rogue Publisher

Authenticity Attack

Attacker generates their own Ed25519 keypair and signs a malicious release metadata payload.

Blocked At: Step 2 (Ed25519 Digital Signature). Client rejects untrusted key.

Scenario 4: Rollback / Replay

Replay Attack

Attacker intercepts valid old v1.0.0 release and replays it to a client already running v1.1.0.

Blocked At: Step 4 (Version & Rollback Validation). Sequence & SemVer check fails.

Scenario 5: Metadata Tampering

Integrity Attack

Attacker modifies the package hash in release.json to match a malicious file, keeping old signature.

Blocked At: Step 2 (Signature Verification). Signature over altered JSON fails.

Scenario 6: Expired Release

Freshness Attack

Attacker supplies correctly signed release whose expiration timestamp is in the past.

Blocked At: Step 3 (Metadata Freshness Check). Expired timestamp rejected.

5. Trust & Key Management

Cryptographic trust anchors, key provisioning, and transport vs payload security boundaries.

Cryptographic Trust Anchors

1. Publisher Private Key (`keys/publisher_private.pem`)

256-bit Ed25519 seed held exclusively by the release authority. Never exposed to web server, CDN, or client. Signs canonical metadata manifests.

2. Client Pinned Public Key (`keys/publisher_public.pem`)

32-byte public key embedded directly within the client software distribution. Serves as the immutable root of trust for verifying all incoming release signatures.

3. TLS Certificate & Authority (`certs/server.crt`, `certs/ca.crt`)

X.509 certificate securing HTTPS transmission. Client authenticates the server domain against its trusted CA store before exchanging metadata or packages.

Transport Security vs. Payload Authenticity

Why HTTPS Alone Is Insufficient:

TLS terminates at the edge. A compromised CDN, malicious proxy, rogue BGP route, or breached update server could serve forged files over valid TLS connections.

End-to-End Release Authenticity:

Ed25519 digital signatures bind the publisher's identity directly to the package digest. Even if updates are distributed over insecure mirrors or untrusted CDNs, the client cryptographically validates authenticity before execution.

Key Rotation Strategy:

In production systems (e.g. TUF), root keys sign intermediate targets keys. During key rotation, the publisher dual-signs releases with both old and new keys during a migration grace window.

6. Security Limitations & Threat Model

Rigorous disclosure of prototype boundaries, architectural assumptions, and production hardening requirements.

Signing Key Compromise High Risk

If the publisher's Ed25519 private key is exfiltrated, an attacker can generate legitimate signatures for arbitrary malware.

Production Mitigation: Air-gapped HSMs (YubiHSM/KMS), multi-signature threshold schemes (TUF Root/Targets delegation), short-lived keys.
Client Host OS / Root Compromise Out of Scope

If malware obtains root or administrative privileges on the client operating system, it can replace the pinned public key, tamper with client code, or edit installed binaries.

Production Mitigation: UEFI Secure Boot, TPM hardware attestation, OS kernel integrity policies (AppLocker/dm-verity).
Local Rollback State Manipulation Medium Risk

The client currently stores version history in `demoapp/state.json` on unencrypted local disk. A local non-root process with write permissions could reset the sequence to 0.

Production Mitigation: Storing monotonic counters in TPM NVRAM or OS-protected credential registries.
System Clock Trust & NTP Spoofing Medium Risk

Release freshness verification relies on `datetime.now(timezone.utc)`. If the client system clock is set backwards via unauthenticated NTP, an expired release could be accepted.

Production Mitigation: Network Time Security (NTS / RFC 8915), consensus timestamps, or server-signed challenge nonces.
Catastrophic Power Failure During Swap Low Risk

While the installer uses staging directories and preserves a `.backup` directory, an abrupt power cut during directory rename could leave files in an intermediate state.

Production Mitigation: A/B dual partition switching or atomic symlink swapping on modern filesystems.
Server Freeze Attacks Medium Risk

A compromised update server cannot forge updates, but it can withhold new security patches, keeping clients on their current version until expiration.

Production Mitigation: Short-lived timestamp metadata roles (TUF) and client-side heartbeat monitoring with out-of-band alerts.
